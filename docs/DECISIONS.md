| D-028 ✅ | **Git-based updates act on one server at a time** (Operations → Updates): fast-forward only, refuse dirty/diverged/detached checkouts, never reset; state travels through the heartbeat row, commands over the bus; restart exits `75` for a supervisor or self-respawns | Every server has its own checkout behind the ALB, so "update the app" must be per server to keep a rolling deploy; a bare `git pull` can merge or clobber local edits | No one-click "update the whole cluster" and no rollback button yet; container images (no `.git`) are out of scope |

| D-029 ✅ | **Rich text = Editor.js-compatible block JSON with our own small Alpine editor**; sanitised server-side on save and again on render | No build step and nothing to vendor; the stored format stays portable to Editor.js; the browser is never trusted with HTML | Fewer block types than Editor.js plugins offer; formatting uses `execCommand` (deprecated but universal) |
| D-030 ⏳ | **Media storage: a storage adapter, with a local-folder implementation that must be a shared volume in a cluster.** S3 is _not built_ (open decision #2) | Works today on one server and on EFS/NFS; the adapter is the seam for S3 | A cluster without a shared volume will lose uploads on other nodes; build the S3 adapter when you choose it |
| D-031 ✅ | **Themes run in a LiquidJS sandbox**: virtual file system, auto-escape with an explicit `Safe` type, allow-listed tags/filters (`raw`, `include`, `sample` removed), render time and memory limits, install-time dry run; **installed themes live in the database, built-in ones on disk; JavaScript in themes is refused by default** | Third-party themes must not be able to read the server, break out of escaping or hang a node; DB storage puts an install on every node at once | Theme JS shares the admin's origin, so allowing it (Settings → Themes) is a trust decision; revisit if outsiders will ever install themes |
| D-032 ✅ | **Page cache tagged by what a page shows, with a deliberately narrow invalidation rule** (body edits touch the entry; renames also touch tree + menu; drafts touch nothing shared); one shared 404 entry | "Editing a page refreshes exactly its cached URLs"; unbounded 404 keys would let anyone fill the cache | A new dependency of a page must add its tag in `render.js` `staticTags` or the page can go stale |
| D-033 ⏳ | **Search is database-native** (FTS5 / FULLTEXT / tsvector) behind one interface — the proposed default for open decision #3 | Nothing extra to run; works on every supported engine | No typo tolerance or per-language stemming; MySQL ignores 1–2 letter words and stop-words; move to Meilisearch/OpenSearch behind the same interface if relevance matters |
| D-034 ⏳ | **Languages: data model + routing only** (locale + translation group on entries, `/<code>/…`, `hreflang`), behind `features.multilingual` — open decision #4 (needed at launch?) stays open | Cheap now, expensive to retrofit into content and URLs | No translation workflow, per-language menus or theme string management beyond `locales/` |
| D-035 ✅ | **The public site is a "site tree" of pages and components, stored in the database and mirrored to a local `public/` folder on every server** (`site_files` + `site_meta.version`; in-memory snapshot to render from; bus + polling to sync; hand edits kept as `.local`) | The site should be files you can browse, diff and commit, but a cluster has no shared disk and the admin must edit it. The database is what every server already agrees on (owner chose "database + local copy" over git-only or shared storage) | The mirror is derived and can lag a poll interval; theme files are not mirrored yet |
| D-036 ✅ | **A theme is the frame, not the content**: layouts, common components, styles, scripts, locales, assets. Templates reach two namespaces only, `{% render "x" %}` (site) and `{% render "theme/x" %}` (theme); switching themes changes the second and never the first. Extends D-031 (sandbox, DB/disk storage): `theme.json` may list `styles`/`scripts`, and a theme needs `layouts/default.html` _or_ the classic pair | "On changing the theme, only theme-level components should be impacted and not the complete site" | Two theme models coexist until the classic `templates/` are retired (SITE-STRUCTURE §8); site components that use theme CSS variables adopt the new palette by design |
| D-037 ✅ | **A component is one HTML file**: Liquid template + scoped `<style>` + a JSON meta block (props, declared API endpoints). Scoping is a selector prefix on a wrapper attribute (`[data-c=id]`, `:host` = the wrapper), css emitted once in `<head>`. `<script>`, `@import` and code-running css are refused for now | No build step and works in every browser (native `@scope` isn't everywhere yet); one file is what a builder edits and what a plugin ships | Keyframe names are global; API endpoints are validated but not executed until the builder; scripts wait for the libraries manager and a CSP/nonce decision |
| D-038 ✅ | **Site-tree edits refresh every cached public page** (`sitefiles` tag on all pages), a deliberate exception to D-032's narrow rule. **Site pages win over content pages at the same address**, and seeding the starter site is an explicit step, never automatic | A new page can change which handler answers an address, so even a cached content page can be wrong; an automatic seed would replace the homepage of an installation already in use | Editing a component clears the whole page cache; refine with a dependency scan when it hurts |
| D-039 ✅ | **One system: every address is a page of the site tree; content is data.** The classic `templates/`/`snippets/`/`layouts/theme.liquid` model and the content-model routing (blog, category, search, content pages, per-type templates) are removed. Content reaches templates only through the `api` endpoints a component declares, run in-process against one public data layer that also backs `/api/public`. Supersedes the coexistence in D-038 and the classic template model of D-031 (its sandbox, DB/disk storage and limits stay) | Two ways to show a page meant two mental models, two theme formats and code that only made sense next to the other; owner: "update the whole new system", "blog and content pages move into components" | Every site needs its pages (the starter site provides them); component authors write Liquid + declared endpoints instead of relying on template variables |
| D-040 ✅ | **Addresses are files**: `[param]` and `[...rest]` in page names, most specific first; `entry:` / `terms:` front matter says which content a page shows and is how an entry gets its address (menus, sitemap, search, previews). A 404 for an address that matched a page (catch-all whose data is missing) is never stored in the page cache | Routing and content addresses without a configuration screen; per-address 404 entries would let anyone fill the cache | A content type with no page has no address |
| D-041 ✅ | **The site ships in `site/`**: `site/defaults` (starter pages, components, locales) and `site/themes` (built-in themes); `public/` is only this server's mirror. An **empty site tree is seeded with the starter site at start-up** (supersedes D-038's "seeding is explicit": with no content routing left there is nothing to shadow, and an empty tree shows nothing) | One place for what the code ships; a site with no pages would be a blank site | An owner who deletes every page gets the starter site back on the next start; `site:seed` never overwrites a non-empty site |
| D-043 ✅ | **`site/` is read-only; language edits live in the tree's `locales/`.** Three layers, highest first: edited (`locales/<code>.json` in the site tree, mirrored to `public/locales`), shipped (`site/locales/<code>.json`, delivered with the code, never written at runtime), theme. Supersedes the part of D-042 that put the starter's English in the tree | Deploys can replace shipped wording without clobbering editors; the database holds only what a human changed; removing an edit restores the shipped text | The starter no longer seeds a `locales/` file, so a fresh site's tree has none until someone edits |
| D-042 ✅ | **Languages merge the theme's and the site's locales; the site wins**, per key, in the visitor's language with base-language/default/English fallback. A language exists when either has a file (or Settings lists it); the site's locales are files of the site tree, edited in the CMS (Translations), and only the site's overrides are stored | Editors re-word anything a theme ships and keep it across theme changes; adding `fr.json` anywhere makes French available | Language names come from the platform's ICU data; content entries still need their own per-language translations |
