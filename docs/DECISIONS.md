| D-045 ✅ | **Services (Webmaster → Services): a query-builder mode AND a raw-SQL mode, on one flat permission set** (`services.read`/`write`/`sql` — not per-item like content types, since a Service has no per-item authorship or publish workflow). Query mode is structurally bounded to `content.listPublished`/`findPublished` (no path to a join or an arbitrary table). SQL mode is real but the safety layers are **asymmetric across engines, by design, and stated as such rather than oversold**: the single-statement + must-start-with-SELECT/WITH check is the actual backstop on PostgreSQL (its simple-query protocol allows `;`-stacked statements when a query has zero parameters — confirmed live, a stacked `DROP TABLE` succeeded before this check existed), where SQLite/MySQL already refuse multi-statement text at the driver level; the keyword blocklist is the primary defense against a write (a rolled-back transaction is not reliable — MySQL DDL auto-commits inside one); a per-dialect statement timeout is real cancellation on PostgreSQL (`SET LOCAL statement_timeout`, value inlined because Postgres's `SET` rejects a bound parameter), real on MySQL for genuine row-scanning work via `SET SESSION MAX_EXECUTION_TIME` (confirmed **not** to interrupt `SLEEP()` specifically — only a real query scan), and not possible at all on SQLite (`better-sqlite3` is synchronous, dev/test only per D-018). A Service result is never marked cacheable (v1). Two independent gates: `features.services` (in-process, a component reading it) and the existing `features.public_api` (the HTTP surface) | Gives admins genuine custom data access without opening a new query engine for the common case, and without pretending SQL mode is uniformly safe when it structurally isn't | `services.sql` must never be granted in a seed role besides the wildcard administrator; query mode has no single-item lookup yet (list only); customer-role scoping (`access: 'customer'`) is stored now but has no effect until customer accounts exist (Phase 2 of the same plan) |
| D-046 ✅ | **Services gains a script mode** (`ctx.services`, `mode: 'script'`) — full, unsandboxed Node.js: the saved code runs as `new AsyncFunction('req', 'ctx', code)` against the real request and the **entire** platform `ctx`, no isolate, no allow-list, same trust tier as shell/console access — and **query mode gains a table/view source** alongside the existing content-type source, selectable from **every table except a hardcoded blocklist** (not an allow-list). New permission `services.script` (on top of `services.write`, escalating past `services.sql`); the table-source query also requires `services.sql`, since it's a step toward arbitrary-table access even though it goes through Knex's query builder, not raw SQL | Owner asked explicitly for "complete Node.js scripts or controllers" and "query builder over raw tables/views" — both real gaps in D-045's scope, and the owner chose the maximum-power option for each ("full Node.js access, no sandbox — exactly as asked"; "everything except a hardcoded blocklist") over a safer default | A script service can do anything the process can (read secrets, write any table, `import()` anything) — never grant `services.script` in a seed role besides the wildcard administrator; the blocklist is the only thing keeping table-source query mode off `users`/`sessions`/etc., so extending it later means extending the `SENSITIVE_TABLES` set, not adding a second check |
| D-047 ✅ | **System → Database (DBMS): full database admin** — table/view list (blocklist-filtered, same idea as D-046's), structure + index introspection, generic row CRUD via Knex, table create/drop, and an **unrestricted raw-SQL console** (`dbms.query`, same "no sandbox" philosophy as D-046's script mode — the console can reach sensitive tables on purpose, that's what a console is for). Flat permission tiers: `dbms.read` (browse/structure) → `dbms.write` (CRUD + create/drop, blocklist-guarded) → `dbms.query` (raw console, blocklist does **not** apply). Its own copy of the sensitive-table blocklist, deliberately not shared with `services/service.js`'s copy, so the two can diverge independently. Column-type-to-Knex mapping has **no native date/time type** on purpose — this platform stores every timestamp as epoch-ms BIGINT (D-011); "Big whole number" is how an admin adds one from this screen | Owner asked for "managing Database and its contents — view all tables, their data, structure, index, create new table, add/edit/delete records, run queries, save queries" — a full DBA console, in the same "trust the operator" spirit already established for `services.sql`/script mode | `dbms.query` must never be granted in a seed role other than the wildcard administrator, exactly like `services.script`; a saved query is stored in plain text in `dbms_saved_queries` (itself blocklisted from the structured UI) since it is the admin's own authored SQL, not a secret in the D-010 sense |
| D-048 ✅ | **Admin menu: "Appearance" renamed to "System"** (themes, translations and the new Database screen live there) **and Webmaster moved above Content**; **Pages, Components, Services and Translations each gained zip export/import** (`GET .../export`, `POST .../import`), reusing the theme-zip safety checks from D-031 (path traversal, absolute paths, symlinks, `__MACOSX`/`.DS_Store` filtering) rather than inventing a second archive-safety path | Owner asked for the reorg directly and for portable backup/migration of each of the four resource types | Import is an **upsert** (create-or-update by slug/path), never a destructive full-replace, so it can't be used to prune a whole set on its own; a "prune" checkbox is offered separately where deleting removed items makes sense (pages/components) |
