| D-045 ✅ | **Services (Webmaster → Services): a query-builder mode AND a raw-SQL mode, on one flat permission set** (`services.read`/`write`/`sql` — not per-item like content types, since a Service has no per-item authorship or publish workflow). Query mode is structurally bounded to `content.listPublished`/`findPublished` (no path to a join or an arbitrary table). SQL mode is real but the safety layers are **asymmetric across engines, by design, and stated as such rather than oversold**: the single-statement + must-start-with-SELECT/WITH check is the actual backstop on PostgreSQL (its simple-query protocol allows `;`-stacked statements when a query has zero parameters — confirmed live, a stacked `DROP TABLE` succeeded before this check existed), where SQLite/MySQL already refuse multi-statement text at the driver level; the keyword blocklist is the primary defense against a write (a rolled-back transaction is not reliable — MySQL DDL auto-commits inside one); a per-dialect statement timeout is real cancellation on PostgreSQL (`SET LOCAL statement_timeout`, value inlined because Postgres's `SET` rejects a bound parameter), real on MySQL for genuine row-scanning work via `SET SESSION MAX_EXECUTION_TIME` (confirmed **not** to interrupt `SLEEP()` specifically — only a real query scan), and not possible at all on SQLite (`better-sqlite3` is synchronous, dev/test only per D-018). Two independent gates: `features.services` (in-process, a component reading it) and the existing `features.public_api` (the HTTP surface) | Gives admins genuine custom data access without opening a new query engine for the common case, and without pretending SQL mode is uniformly safe when it structurally isn't | `services.sql` must never be granted in a seed role besides the wildcard administrator; query mode has no single-item lookup yet (list only); customer-role scoping (`access: 'customer'`) is stored now but has no effect until customer accounts exist (Phase 2 of the same plan) |

| D-051 ✅ | **Scheduler (Automation → Scheduler), Phase 2 of the Events/Webhooks/Scheduler plan**: admin-editable recurring automation — run an existing Service, or fire a Webhook, on an interval (≥ 1 minute) or a cron expression.
