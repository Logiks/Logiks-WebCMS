# Project plan — CMS + eCommerce platform

_Last updated: 2026-09-22 · Owner: BKM (SmartinfoLogiks) · Status: Phase 1 complete (one owner confirmation open: 1e); Phase 2 built but not yet audited against its exit criteria; M2.6 (the site, one system) and its page/component builder done_

**How to read this:** Phase 1 describes what exists and what is still open (verified against the code and tests).
Phases 2–4 are a **proposed breakdown** of the four-phase, ~25-week plan agreed earlier. The phase boundaries and themes are agreed;
the milestone detail, estimates and targets below are proposals to confirm or change. Items marked **❓** need a decision from the owner
(see [Open decisions](#open-decisions)).

## 1. Goal and scope

A single-site CMS with an admin console and a public website, plus an online store, that runs as a **multi-server cluster behind one
AWS ALB** with most configuration in the database. Third-party themes must be safe to install.

**In scope:** content management, themes, media, SEO, public API, catalog, cart/checkout, orders, GST-aware tax, payments
(pluggable: Stripe, Razorpay, PayU, COD), extensibility (modules), hardening, launch tooling.
**Out of scope (for now):** multi-tenant hosting, vendor payouts/commission (data-ready multi-vendor is in, D-090), mobile apps, a visual page builder beyond block editing,
e-invoicing/e-way-bill filing (hooks only), multi-currency accounting.

## 6. Phase 3 — eCommerce (planned, D-088..D-100)

**Outcome:** a business customer or consumer can browse a large catalog, download specifications, request a quote or buy and pay, and the merchant can fulfil, invoice and report — with correct Indian GST. Scale target: **100k SKUs, 100k+ orders/day**.

Shape: an **independent Product Catalog** (not content types), **pluggable** payment gateways, file storage and search, a default "house" vendor so multi-vendor is data-ready but invisible, and **request-a-quote** for products without a public price. Everything sits behind `features.commerce` (off by default).

### Features: the switch for whole subsystems (D-100)

**Settings → Features** is the main place to turn subsystems on and off: **Blog, eCommerce, Payment gateways, Support tickets** (and Customer accounts, which others pull in). A feature is a named bundle of **modules, plugins and seeded pages/components**; **System → Modules** stays as the advanced per-module view of the same switches.

- **Dormant until enabled:** no menu items, routes, public pages, API operations or jobs. Tables exist (they ship with every deploy), empty.
- **Enabling** turns on the bundle's modules and their dependencies (shown before you confirm) and **seeds pages/components once** into the site tree, in the active theme's frame (theme tokens and layout; the site's own wording through translations). After that they are ordinary editable site files.
- **Disabling never deletes.** Data stays; seeded pages are tagged with their feature and simply stop being served; re-enabling restores them. Edited pages are never overwritten by a re-enable.
- **Blog becomes a feature** (on for existing installs, off for new ones).
- **Payment gateways** is its own feature so each gateway can be switched on separately; it needs eCommerce's checkout.

**What AI can change:** plugins, pages, components, message templates, scripted Services. **Core module logic stays intact** (stock, GST, orders, payments). Customisation of core behaviour goes through the **rules engine** (`commerce-rules`) below, and a module can be **forked into a plugin** that AI may then edit freely (needs the plugin extension points, milestone E4 — see below).

**Rules engine (`commerce-rules`, eCommerce, off by default):** admin-defined, ordered, auditable rules of _conditions → actions_, evaluated by core at fixed hook points: cart totals and line adjustments, payment-method availability (e.g. COD limits), shipping eligibility and fees, checkout validation, order auto-flags. Conditions read cart, customer group, region, SKU/category/brand attributes and order history; actions are limited to what each hook allows (add fee, hide method, block with a message, flag order). Has a **simulator** (try a rule against a sample cart) and a log of which rule fired. Data (JSON), not code, so it is safe to let AI draft rules for a human to approve. Promotions (E4) will be built on it.

**Fork to plugin:** a module's source is copied into `plugins/<slug>/` with ids renamed; the original stays untouched. It needs plugins to declare settings, content types, Liquid tags, events and services on `ctx` (D-060's "not yet built" list), so it is scheduled as E4, after the core ships.

**Migration rule restated:** tables and columns are created by migrations on deploy, **additive only**. A column or table holding data is never dropped or rewritten in the same release that stops using it (expand/contract).

### Customer sign-in and registration (D-096)

Off until the `customers` module is on **and** registration is enabled in its settings (so a store can show the catalog only).

- **Identifier:** email, mobile, or either — a setting. **Password** always; **OTP** for verifying a new email/mobile, for sign-in as a second step or passwordless fallback (setting), and for password reset.
- **OTP rules:** stored hashed, short expiry, limited attempts, resend cooldown, per-identifier and per-IP rate limits. Email goes through the existing mailer; **mobile needs an SMS provider adapter** (pluggable, like gateways; India needs DLT-registered templates).
- **Fraud lock:** deterministic, configurable rules score each account (many sign-ups from one IP or device, disposable email domains, OTP request bursts, repeated failed OTPs, repeated failed or declined payments, repeated COD refusals). Past the threshold the account becomes **locked until an admin acts** (unlike the timed lockout admin users get): sessions end, sign-in says to contact support, and the customer is never told which rule fired. The reason and signals are recorded.
- **Admin:** a **Flagged accounts** screen lists locked accounts with the signals; an admin **activates** (with a note, audited) or keeps them locked. An activated account gets a grace period so the same signals don't re-lock it at once.
- Customer sessions are a **separate auth realm** from admin users; account pages are never cached.

### Contact Us and tickets (D-097)

`support` (category **Support**, off by default; works without commerce): a public Contact Us form creates a **ticket** for staff. A ticket has a reference number, subject, message, attachments (through file storage), status (open → pending → resolved/closed), priority, assignee, internal notes and a threaded reply history emailed to the sender. Backend is a **simple grid** (sortable, filterable by status/priority/assignee, click a row for the thread and reply box), not a helpdesk suite. Signed-in customers see their own tickets; guests verify with an email or mobile OTP. Emits `ticket.created` / `ticket.replied`. It replaces the plain contact form when on; quote requests (`quotes`) remain a separate inbox.

## 8. Cross-cutting

**Targets to confirm** (proposals, to be measured on the primary DB ❓): cached public page p95 < 50 ms at the app tier; uncached page p95 < 300 ms;
settings propagation to all nodes < 2 s p99; zero failed requests during a rolling deploy at steady load; admin usable at 375 px.

**Testing:** every feature ships with tests at the level users notice it (HTTP, jsdom UI, real SMTP/Redis). Cluster behaviour is tested with
multiple nodes; cross-process where a driver is synchronous. Bug fix ⇒ failing test first. CI runs the SQLite/MySQL/PostgreSQL matrix.

**Security:** threat-model each new public surface (uploads, themes, checkout, webhooks) before building it; secrets only via encrypted settings;
audit every admin mutation; rate-limit every unauthenticated mutation.

**Operations:** each feature adds its metrics, health signal and runbook note. Migrations are additive.

**Definition of done:** code + tests + docs, `/verify` green, permissions/settings registered, audit written, no secrets in logs, migration
additive, admin copy reviewed, `CLAUDE.md` "Where we are" updated.

## 9. Risks

| Risk                                          | Impact                            | Mitigation                                                                                                              |
| --------------------------------------------- | --------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| MySQL/PG dialect differences                  | Late, expensive surprises         | Suite passes on both; keep the CI matrix mandatory (it has not run on GitHub yet)                                       |
| Third-party theme = code execution risk       | Site takeover                     | LiquidJS sandbox, template limits, validated packages, malicious-template test suite before themes ship                 |
| Payment/tax correctness (GST)                 | Financial and compliance exposure | Money as integers, table-driven tax tests, idempotent webhooks, reconciliation job, accountant review of invoice format |
| Overselling / double orders under concurrency | Lost revenue, trust               | Inventory reservation with row locks, idempotency keys, cross-node concurrency tests                                    |
| Shared file storage in a cluster              | Media missing on some nodes       | S3-compatible adapter as the cluster default; local disk only for single node                                           |
| Scope creep in the theme/page builder         | Phase 2 overrun                   | Block editor + sections only; visual builder is out of scope                                                            |
| Solo-developer bus factor                     | Stalls                            | This plan, `CLAUDE.md`, `DECISIONS.md`, and tests as the living spec                                                    |
